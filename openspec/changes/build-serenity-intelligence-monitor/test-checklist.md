## AC-1 `[用户手动]`：配置真实 X Developer 凭据后，系统能通过合规的官方接口获取至少一条 Serenity 新内容，并保留来源 URL、平台 ID、作者、原文、发布时间、获取时间和原始响应审计信息；若凭据或 credits 未提供，验收报告必须明确标为“尚未真实 API 验证”，不得用 Mock 冒充。

### TC-1.1：真实 X 凭据完成单条内容获取与审计

- **类型**: `[用户手动]`
- **前置条件**:
  - 已在服务端配置有效的 X Developer Bearer Token、可用 credits 和 Serenity 账号映射，且已完成人工政策复核；测试账号存在至少一条可访问内容。
  - API、worker、MySQL 和 Redis 正常运行，验收人员持有管理员登录凭据。
- **测试步骤**:
  1. 在服务器端配置真实 X 凭据并启动同步，不在浏览器、日志或请求参数中粘贴 Token。
  2. 操作路径：浏览器打开 `/login` 登录，进入 `/status`，触发或等待一次 Serenity 轮询并确认该轮询成功。
  3. 操作路径：从 `/` 的最新情报列表打开新内容，进入 `/intelligence/:id`。
  4. 将详情页展示和服务端审计记录与 X 上的同一条真实内容逐项核对。
- **预期结果**: 详情和审计中可判定地存在同一条内容的来源 URL、平台 ID、作者 `@aleabitoreddit`、原文、发布时间、获取时间及不含 Authorization/Token 的原始响应审计信息；验收报告将本次证据归类为“真实 X API 已验证”，且相关字段与真实来源一致。
- **证据类别**: `真实 API 已验证`；执行方式为用户手动，保存脱敏的 `/status` 成功截图、`/intelligence/:id` 字段截图、X 来源页截图及对应 ingestion run/provider request ID。

### TC-1.2：缺少凭据或 credits 时不得以 Mock 冒充真实验证

- **类型**: `[用户手动]`
- **前置条件**:
  - 使用隔离验收环境，移除 X Bearer Token 或将 credits 置于不可调用状态；环境中允许保留 Mock fixture，但生产同步开关不得指向 Mock。
  - 验收人员持有管理员登录凭据。
- **测试步骤**:
  1. 在缺少真实凭据或 credits 的条件下启动 API 与 worker并尝试执行一次真实同步。
  2. 操作路径：通过 `/login` 登录后进入 `/status`，查看 X 数据源配置和最近一次同步状态。
  3. 查看本次验收报告的 AC-1 证据分类，并检查最新情报中是否出现被标称为“真实 API 获取”的 Mock 数据。
- **预期结果**: `/status` 明确显示 `blocked` 且 `block_reason=configuration|budget` 或等价的失败可见状态；验收报告明确写“尚未真实 API 验证”；Mock 只能标为 Mock，不产生任何被标成真实 X API 获取的记录，也不得将 AC-1 标记通过。
- **证据类别**: `待人工配置或验证`；执行方式为用户手动，保存脱敏状态页截图、失败审计记录和验收报告分类，不记录 Token 值。

## AC-6 `[用户手动]`：使用 OpenAI `gpt-5.6-terra` 的真实 Responses API 调用抽查研究卡片时，输出通过严格结构化契约且保持证据边界。

## AC-7 `[AI自测]`：重要性由可配置的结构化规则和可解释分项共同决定；高价值 fixture 进入通知队列，普通/低价值 fixture 仅归档，阈值变化可测试且不由模型任意覆盖。

  - 为数据源中断、429 限流、上下文补全失败、模型失败、通知失败分别准备“一次失败后成功”的 fixture。
- **测试步骤**：
  1. 参数化运行五类暂态故障，记录首次 attempt 的 stage、错误分类和状态。
  2. 推进退避时间或运行 reconciliation，确认任务被重新排队并在恢复后完成。
  3. 在任一处理中阶段模拟进程退出，保留数据库状态并丢弃进程内状态。
  4. 重启 worker、推进 lease 到期并运行 reconciliation，查询最终 attempt 链和业务结果。
- **可判定预期**：每次暂态故障均先产生可见失败 attempt，再生成新 attempt 并最终成功；进程重启后从数据库审计状态续办，不重复完成业务副作用；不存在把首次失败记为成功或无记录丢失。
- **证据类别**：`Mock 已验证`（自动化恢复测试输出、attempt 状态链和适配器调用计数）；**用例检索依据**：`openspec/changes/build-serenity-intelligence-monitor/.cheap-search-report.md`。

### TC-13.2：永久故障耗尽重试后进入明确终态/死信（异常/边界）

- **类型**：`[AI自测]`
- **前置条件**：
  - Mock 持续返回不可恢复认证/权限错误，或持续失败直至达到最大重试次数。
  - 状态查询和显式人工重试接口可在测试中读取。
- **测试步骤**：
  1. 运行持续失败任务直至达到最大 attempt，记录每次错误分类和退避。
  2. 运行 reconciliation 两次，确认其不会把已终态任务自动标记成功或无限重排。
  3. 查询终态/死信记录和状态摘要。
  4. 由管理员显式重试一次，核对是否创建新 attempt 而不覆盖原终态链。
- **可判定预期**：任务明确进入 `dead_letter` 且 `manual_retry_allowed=true`，包含 stage、错误分类和历史 attempt；重复 reconciliation 不产生静默成功、静默丢失或无界重试；管理员重试创建新 attempt chain 并保留独立审计记录。
- **证据类别**：`Mock 已验证`（自动化死信测试、状态查询结果和 attempt 链）；**用例检索依据**：`openspec/changes/build-serenity-intelligence-monitor/.cheap-search-report.md`。

## Repair lane 验收规则

1. **第 1 类——实现未满足既有规范**：仅在当前 change 内做最小修复；必须新增命中原失败路径的回归测试并重跑受影响 AC。不得借修复扩大目标范围。
2. **第 2 类——原目标必要行为但规范遗漏**：必须先同步回写 `proposal`、相关 spec、`design`、`test-checklist` 和 `tasks`，再重跑受影响的规范审查、代码审查与测试；回写前不得直接以实现补洞。
3. **第 3 类——新增需求或范围扩大**：必须新建 change；多账号、新闻抓取、A 股公司级自动映射、新通知渠道等不得塞入本 change。
4. **第 4 类——环境、数据或操作问题**：先用 ingestion run、processing attempt、provider request ID 及操作记录复现和解释；未证明为业务缺陷前不得修改实现。
5. **归档门禁**：第 1、2 类问题未关闭不得归档；任何修复不得通过降低断言、伪造 Mock、删除失败证据或把待人工项标为通过来收敛。

## 四类证据边界

| 证据类别 | 可证明 | 不可冒充/限制 |
|---|---|---|
| `自动化已验证` | 本地或 CI 中可重复的单元、集成、E2E、构建、静态扫描与确定性运行结果 | 不能证明真实外部账号、网络、配额、政策、Webhook、Docker 目标环境或生产部署可用 |
| `Mock 已验证` | 适配器契约、故障注入、重试、幂等、预算、限流及安全边界在受控替身下的行为 | 不能写成真实 X/AI/飞书调用成功，也不能证明真实成本、配额、签名或供应商返回兼容 |
| `真实 API 已验证` | 使用已授权真实 X/AI/飞书环境完成的脱敏联调；证据须含时间、操作、provider/request ID 或等价回执及成本/资源记录 | 不得仅凭 Mock、截图样例、文档推测或无可追溯响应判定；不得在证据中暴露 Secret |
| `待人工配置或验证` | 尚需用户凭据、政策确认、Docker/部署环境、HTTPS/Secure Cookie、网络边界或质量抽查的项目 | 在人工操作和原始证据完成前必须保持未通过，不得由自动化或 Mock 代替 |
