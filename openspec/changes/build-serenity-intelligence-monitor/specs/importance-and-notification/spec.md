## ADDED Requirements

### Requirement: 重要性必须由可解释的确定性评分器计算
系统 MUST 使用版本化权重和阈值对结构化特征计算重要性，模型提供的候选特征 MUST 带证据且不得直接覆盖服务端通知决策。

#### Scenario: 高价值内容达到阈值
- **WHEN** 经校验的分项特征计算结果达到通知阈值且置信度不低于要求
- **THEN** 系统保存每个分项、权重快照、总分、阈值、版本与解释
- **AND** 创建通知候选

#### Scenario: 低价值或无法评分
- **WHEN** 内容总分低于阈值、置信度不足或关键证据缺失
- **THEN** 系统完整归档内容与卡片但抑制即时通知
- **AND** 保存可理解的抑制原因

#### Scenario: 阈值配置变化
- **WHEN** 同一结构化特征使用不同版本阈值重新计算
- **THEN** 决策随实际阈值确定性变化并保留各自配置快照
- **AND** 模型输出的相反提醒建议不能覆盖计算结果

### Requirement: 通知必须稳定去重并可恢复
系统 MUST 以渠道、内容事件和提醒策略形成用户感知去重，并以内容/卡片/策略版本形成技术 delivery 键；系统 MUST 记录发送状态、attempt、provider ID 和失败类别，且 MUST 对发送结果未知使用独立状态。

#### Scenario: 重复创建同一通知
- **WHEN** 同一通知候选被重复入队或 worker 并发处理
- **THEN** 系统只保留一个 delivery 并最多成功发送一次
- **AND** 重复作业返回既有结果或安全跳过

#### Scenario: 通知明确失败
- **WHEN** 飞书适配器在请求发送前失败或返回明确拒绝、429 或 5xx
- **THEN** 系统记录可重试失败并按策略创建新 attempt
- **AND** 恢复后只完成一个技术 delivery

#### Scenario: 通知发送结果未知
- **WHEN** 请求可能已被 provider 接收但本地响应超时，或发送后在保存结果前进程崩溃
- **THEN** delivery 进入 `outcome_unknown` 并在状态页显示
- **AND** 系统不得盲目自动重发，只有管理员核对或 provider 幂等/查询能力得到真实验证后才能继续

#### Scenario: 同一内容被模型或策略重算
- **WHEN** 原文未发生实质编辑，仅模型、prompt 或评分策略版本变化
- **THEN** 系统保存新的分析审计但不再次提醒用户
- **AND** 只有实质内容/观点变化或管理员明确重发才能创建新的用户提醒事件

#### Scenario: 通知配置错误
- **WHEN** Webhook 缺失或 provider 返回不可恢复 4xx
- **THEN** 系统进入待配置或终态失败并在状态页显示原因
- **AND** 普通内容归档不受影响

### Requirement: 第一阶段只实现飞书生产通知适配器
系统 MUST 通过服务端 `NotificationAdapter` 实现飞书自定义机器人通知；QQ 与邮件只能保留抽象边界，不得在本 change 增加生产实现。

#### Scenario: 真实飞书提醒成功
- **WHEN** 管理员配置真实飞书 Webhook 且高价值内容通过通知策略
- **THEN** 系统发送一条保留来源和不确定性标签、包含重要性理由和绝对 HTTPS 私有详情链接的提醒
- **AND** 消息与日志均不包含 Secret 或未验证的 A 股受益名单

#### Scenario: Webhook 未配置
- **WHEN** 高价值内容产生但飞书 Webhook 缺失
- **THEN** delivery 标记为待配置而不是已发送
- **AND** 验收报告不得把 Mock 发送写成真实飞书验证
